## 2026-05-26 (later 2) — retry 스레드 인식 실패 버그 픽스

### 원인

install은 create_job(slack_thread_ts=None) → notifier 호출(객체에만 세팅) 순서라
DB는 영원히 NULL.

  같은 값이 들어있어 idempotent

  스텁 notifier로 검증

## 2026-05-26 (later 4) — sudo 비밀번호 자동 주입 (stdin)

### 배경
앞 패치 직후 #7 작업이 `sudo: a terminal is required to read the password`로
실패. connecteve 계정이 NOPASSWD가 아니라 sudo가 비밀번호를 요구했고, 봇은
비대화형 SSH라 입력 불가. 그런데 .env에 이미 SSH_PASSWORD가 있고 sudo도
같은 계정 비밀번호를 쓰니, 그걸 stdin으로 흘려넣으면 됨.

### 구현 (176/176 통과)
- scripts.py `_sudo_prefix(password)` 도입.
  - 비밀번호 없으면 `sudo` (기존 동작 유지, NOPASSWD 환경)
  - 비밀번호 있으면 `printf '%s\n' '<pw>' | sudo -S -p ''` (stdin 주입)
  - `printf`는 bash 빌트인이라 별도 프로세스 안 생김 → ps에 비밀번호 노출 X
  - shlex.quote로 특수문자(#$) 안전
- run_script에 `sudo_password: str = ""` param 추가
- workflow.install_missing_tools에 동일 패턴 적용 (apt-get update + install을

## 2026-05-26 (later 7) — work_dir 의 `~` literal 폴더 버그 픽스

### 증상
타겟 서버에서 `ls ~` 했을 때 `'~'` 라는 literal 폴더가 있고 그 안에

### 원인
git_sync.py에서 `shlex.quote(work_dir)`로 경로를 감싸는데, work_dir이
`~/gateway-infra-next`로 들어오면 `'~/gateway-infra-next'`가 됨. bash의
tilde expansion은 **단일 인용 안에서 동작하지 않아**서 `~`가 literal로 처리됨.
→ 봇이 `git clone ... '~/gateway-infra-next'`로 호출하면 진짜로 `~`라는
이름의 폴더가 홈 디렉토리에 생기고 그 안에 clone됨.

### 픽스 (181/181 통과)
- settings.py: `_expand_remote_home(path, ssh_user)` 헬퍼 추가.
  로드 시점에 `~/foo` → `/home/<ssh_user>/foo`로 치환. 이후 모든 코드가
  절대경로만 다루게 됨. shlex.quote로 감싸도 안전.
- 신규 테스트 3건:
  - test_work_dir_tilde_expanded_to_remote_home
  - test_work_dir_bare_tilde_becomes_home
  - test_work_dir_absolute_path_unchanged
- 기존 `test_loads_minimum_required_env`의 work_dir 단언 갱신

### 운영 후속 (타겟 서버 정리)
잘못 생성된 literal `~` 폴더는 사용자가 한 번 정리해야 함:

  rm -rf '~'

그 다음 봇이 새 절대경로(/home/connecteve/gateway-infra-next)로 clone.

## 2026-08-26 (밤) — SSH 키 등록 자동화 추가 (F9)

### 배경
용혁이 runbook §1-1(SSH 키 등록)을 설치 흐름에 넣어달라고 요청.
원문 요청은 "설치되는 서버에서 ssh-keygen, 맥미니에서 ssh-copy-id" 였는데
동작상 keygen은 컨트롤러(맥미니)에서 해야 맞음 — 확인 결과 용혁 의도는
"타겟에 ~/.ssh 디렉터리를 만들려는 것"이었음.
→ 타겟에서 ssh-keygen 안 함. `mkdir -p ~/.ssh && chmod 700` 으로 대체.
   (납품 서버에 쓰지도 않을 개인키를 남기지 않기 위함)

### 실측
- 맥미니에 `~/.ssh/id_ed25519(.pub)` 이미 존재 → keygen 단계는 실제로 skip됨
- `/usr/bin/ssh-copy-id` 존재하나 사용 안 함 (비대화형 어려움)
- `.env` 에 SSH_PASSWORD 설정돼 있음. 단 D9에서 "매번 입력" 으로 결정 —
  서버마다 비밀번호가 다를 수 있어 .env 값을 자동으로 쓰지 않음
- 기존 `AsyncSSHClient` 가 이미 `known_hosts=None` + password 지원 →
  ssh-copy-id / sshpass 없이 asyncssh 만으로 구현 가능 (새 의존성 0)

### F9 설계 (dev-spec v1.1 에 반영)
서버 1대당 한 번:
1. 컨트롤러 키 확인 (없으면 ssh-keygen -t ed25519 -N "" 자동 생성)
2. 타겟에 비밀번호로 접속 (웹 폼에서 1회 입력, 메모리에만)
3. `mkdir -p ~/.ssh && chmod 700` → `grep -qxF` 로 중복 확인 후 authorized_keys append
   → chmod 600  (재실행해도 줄 안 늘어남 = 멱등)
4. **비밀번호를 끄고 키 인증만으로 재접속해 검증** — 여기 성공해야 등록 인정
5. `server_meta.key_installed_at` 기록

연동: 서버 목록에 SSH 키 컬럼 + '키 등록' 버튼 / 키 미등록 서버가 선택되면

### 먼저 확인한 것 (추측 금지)
1. 맥미니 sshd 살아 있음 — Tailscale 로 `publickey,password,keyboard-interactive` 응답.
2. `ssh_keys.py` 는 타겟 sshd 의 PasswordAuthentication 을 끄지 **않는다**.

4. **포트가 실제로 넘어가는지 실증**: 127.0.0.1:2222 에 프로브 리스너를 띄우고
   `open "ssh://connecteve@127.0.0.1:2222"` → `SSH-2.0-OpenSSH_10.2` 배너 도착.

### 한 것
- `forwards.py`: `HTTP_PORTS` / `SSH_PORT=22` 로 나누고 `ALLOWED_PORTS` 는 둘의 합.
  `plan()` 엔트리에 `via`(http|ssh) 추가, 터미널은 항상 맨 뒤.
  22 는 `HYBRID_CLOUD_PORTS` 에 없으므로 hybrid 에서도 자동으로 relay — 특별 분기 없음.
- `api.py`: GET 계획 응답에 `user`(= 인벤토리 ansible_user) 추가.

## 2026-08-27 — 절전 끄기를 SSH 키 등록 단계에 넣음

### 배경 (질문에서 출발)
"우분투 잠금방지 명령은 언제 실행되나?" → 확인해보니 **웹 콘솔 경로에서는 아예

(`_step_git_pull` 맨 앞)에만 있고, 콘솔은 `web/jobs.py` → hubctl 로 간다.
hub-provisioning role 들도 절전을 안 건드린다(grep 확인). 게다가 지금
SLACK_ENABLED=false 라 v1 경로 자체가 꺼져 있다 = 아무 데서도 안 걸린다.

### 넣은 자리: register_key
키를 심는 단계는 이미 sudo 가 되는 비밀번호를 쥐고 타겟에 붙어 있다. 자리가 맞다.

### 중요한 설계 판단 두 가지

**1. 비밀번호를 명령줄에 싣지 않는다.**
기존 workflow 구현은 `printf '%s\n' <비번> | sudo -S ...` 였다. 그 줄은 타겟의
`ps` 에 그대로 보인다 — 같은 서버에 로그인한 누구나 볼 수 있다.
게다가 ssh_keys 에는 `test_password_never_appears_in_remote_command` 라는
기존 불변식이 있어서 그대로 옮기면 그걸 깨는 셈이었다.
→ `SSHClient.exec` 에 `stdin` 인자 추가. `sudo -S -p ''` 는 어차피 표준입력에서
  읽으므로 명령줄은 깨끗하게 두고 stdin 으로 보낸다.
  Protocol / AsyncSSHClient / FakeSSHClient 세 곳 갱신 (FakeSSHClient 는 stdins 기록).
  workflow.disable_sleep_targets 도 새 구현으로 넘겨 두 벌이 안 생기게 했다.

**2. mask 실패가 키 등록을 막으면 안 된다.**
키가 없으면 설치를 아예 못 한다. 부수적인 절전 설정 때문에 그걸 막을 이유가 없다.
→ best-effort. `register_key` 반환을 str → `KeyRegistration(pubkey, sleep_masked,
  sleep_error)` 로. API 가 그대로 내보내고, 콘솔은 실패 시 warn 토스트로
  "키는 됐고 절전은 안 됐다 + 직접 실행할 명령" 을 말한다. 뭉뚱그리면 긴 설치가
  한밤중에 SSH 끊김으로 죽고 원인을 못 찾는다.

- API 응답에 sleep_masked / sleep_error
기존 테스트 3개 갱신 (반환 타입 변경, _HangingSSHClient 시그니처).

## 2026-08-27 (이어서) — 콘솔에 패치 화면 추가

### 왜 필요했나
뒷단은 다 있었는데 **입구가 없었다.**
- `hubctl.py` 의 patch create/apply 조립, `jobs.py` 의 승인→apply, 작업 상세의
  `적용 승인`/`거부` 버튼, operations.md §5-5 문서까지 전부 있었다.
- 없는 것: 왼쪽 메뉴의 패치 화면, 그리고 **적용 대상을 지정할 방법**.
- `patch create` 는 `-l` 을 못 받아 create 가 hosts 를 거부했는데(jobs.py:126),
  승인은 job_hosts 에 서버가 있어야 돌았다(jobs.py:227). API 로는 그 사이를 채울
  길이 없었다 — 테스트도 DB 에 직접 INSERT 해서 넘어가고 있었다.

### 결정 (용혁님 선택)
**적용 대상은 패치 화면에서 미리 고른다. 승인 화면은 확인만 한다.**
승인 시점에 고르게 하면 번들을 다 만들어 놓고 나서야 "SSH 키가 없는 서버" 를
알게 되고, 그러면 그 번들이 갈 곳이 없다. 미리 고르면 AC-16 이 번들 생성 전에
걸러준다.

### 구현
- `create()`: 종류와 무관하게 `_check_hosts` 를 태워 대상을 검증하고 job_hosts 에
  기록. 명령에 실을 대상만 따로 뽑는다 (`command_hosts`) — patch create 는 빈 값.
  덕분에 build_command 가 거부하지 않고, _execute 도 job_hosts 를 안 건드려
  서버들이 '대기' 인 채로 승인을 기다린다.
- `_finalize`: 대상 없이 돈 단계(patch create)가 죽으면 위 루프가 job_hosts 를
  안 건드려 작업은 실패인데 서버는 '대기' 로 남는다 → 남은 줄을 함께 닫는다.
- 화면: 메뉴 `패치` + `view-patch` (서버 다중선택 · ref · 태그 체크).
  명령 미리보기에 **두 줄을 다 그린다** — create 만 그리면 "-l 이 왜 없지" 로
  읽히고, apply 만 그리면 지금 뭐가 도는지 안 보인다.
- 작업 상세: 승인 안내에 적용 대상을 박고, 버튼 문구도 `N대에 적용 승인`.
  대상이 없는 옛 patch 는 버튼을 아예 안 그린다 (눌러도 409).
  승인은 서버를 실제로 바꾸는 유일한 지점이라 확인 모달을 붙였다.

### 덤으로 잡은 버그 — 로그 마지막 줄 유실
전체 테스트를 돌리다 한 번 빨간불이 떠서 파봤더니 진짜 버그였다.
`_LogSink.flush` 는 버퍼를 **통째로 꺼낸 뒤** DB 를 기다리는데, `close()` 가
수집 루프를 `cancel()` 했다. 하필 그 사이에 취소가 들어오면 꺼내둔 배치가
어디에도 안 남고 사라진다 — 그리고 close() 가 불리는 시점이 정확히 작업이
끝나는 순간이라, **마지막 0.15초(= PLAY RECAP 과 오류 줄)가 통으로 날아갔다.**
→ 취소하지 않고 플래그로 세워 하던 flush 를 끝내게 했다. DB 가 걸려 close() 가
   안 끝나는 것만 wait_for(3초) 로 막고, 취소는 거기서만 마지막 수단으로 쓴다.
→ `blocked_connect` 로 flush 를 DB 문 앞에 세워 **결정적으로 재현되는 테스트**를
   먼저 넣고(빨간불: 3줄 전부 유실) 고쳤다.

## 2026-08-27 (이어서 2) — 패치를 원샷(hubctl patch)으로 바로잡음

### 용혁님 지적 — 내가 틀린 모드를 쓰고 있었다
"patch create는 내가 진행하지 않아. 난 `hubctl patch -l ... -- -e hub_deploy_ref=`
로 패치를 진행할꺼야."

`patch-create.yml` 헤더를 읽어보니 둘은 **같은 일을 하지 않는다.**
| | 원샷 `hubctl patch` | `hubctl patch create` |
| 어디서 | 타겟에서(become) | 컨트롤러 로컬 |
| base | 지금 깔린 live release-config | `-e patch_base=<ref>` |
| 용도 | 온라인 | 폐쇄망 반입용 |

앞 커밋(06bd555)은 **폐쇄망 반입 경로**를 온라인 병원에 쓰고 있었고, 그 경로가
요구하는 `-e patch_base` 를 콘솔이 한 번도 안 보냈다.

그리고 `patch create` 는 `-e patch_create_hosts=localhost` 를 run_playbook 인자로
하드코딩한다. `run_playbook` 이 `ANSIBLE_ARGS`(passthrough) **뒤에** 그걸 붙이고
ansible 은 나중 `-e` 가 이기므로, hub-provisioning 을 안 건드리는 한 못 덮는다.
→ 원샷 말고는 온라인 create 로 가는 길이 없다.

### 막힌 지점과 결정
원샷은 create 뒤 `read -r` 로 `[y/N]` 을 묻는다. 그런데 콘솔은 자식에게 stdin
파이프를 안 열어줬다 → `read` 가 즉시 EOF → 매번 "사용자 취소"(rc=2).

용혁님 선택: **시작 전 확인 후 자동 y.**
- 화면 시작 모달이 터미널의 `[y/N]` 을 대신한다 (그래서 모달 문구를 강하게 씀).
- 시작하면 중간에 안 멈춘다. 변경 앱 목록은 로그에 남지만 볼 때는 이미 적용 뒤.

### 구현에서 신경 쓴 것
- **프롬프트 줄은 개행이 없다** (`printf '... [y/N] '`). 줄 단위 펌프(`_iter_lines`)
  는 `\n` 에서만 끊으므로 프롬프트 자체는 EOF 전까지 안 보인다.
  → 개행으로 끝나는 **바로 앞 줄**을 신호로 쓴다 (`PATCH_CONFIRM_MARKER`).
  NO_COLOR=1 + 파이프라 hubctl 의 색 코드는 비어 있어 평문으로 매치된다.
- **auto_reply 가 없으면 stdin 을 곧바로 닫는다.** 안 그러면 stdin 을 읽는 명령이
  (bin/hubctl 에 `read` 는 patch·clean 두 곳) 영영 기다린다. 예전처럼 EOF 받고
  제 안내문과 함께 죽는 편이 낫다. 답한 뒤에도 닫는다.
- 자동 응답을 **job_events 에 기록**한다. 안 남기면 나중에 기록만 보고는 누가
  적용을 승인했는지 알 수 없다.
- 마커가 안 맞으면 작업이 멈춘 채로 남는다 → 일부러 마커를 깨서 확인했다.
  20초 만에 TimeoutError 로 빨간불이 뜨고, 취소(SIGTERM)로 정리된다.

### 남겨둔 것
create/apply 2단계 조립·승인·거부·24시간 자동 취소는 **지우지 않았다.** 폐쇄망
반입은 여전히 그 길이다. 다만 콘솔에서 그 상태로 들어가는 길이 없어져서,

## 2026-08-27 (이어서 5) — 설치 시작 전 hub-provisioning 최신화

### 먼저 확인한 것 (실서버)

- 현재 main / origin/main 추적, 작업트리 깨끗(untracked .bak 하나뿐).

### 결정
- **시점: 실행 직전.** 작업 생성 시점에 당기면 앞 작업이 도는 중에 playbook 이
  발밑에서 바뀐다. 작업은 한 번에 하나만 도니 실행 직전이면 안전하다.
- **실패하면 작업 실패** (용혁님 선택). 타겟을 손대기 전이라 반쯤 된 상태가
  안 남는다. 조용히 옛 버전으로 깔면 "최신 유지" 목적 자체가 없어진다.
- **대상: install · configure · patch(원샷).**
  verify·clean·rollback 은 뺐다 — Bitbucket 이 죽었을 때 오히려 더 필요한
  작업이라 최신화 실패로 손발을 묶으면 안 된다.
  patch 의 apply(2단계 반입 승인)도 뺐다 — 번들은 생성 시점 playbook 으로
  만들어졌으므로 그 사이 저장소를 바꾸면 앞뒤가 어긋난다.

### `git pull` 을 안 쓴 이유
fetch → checkout → merge --ff-only 로 나눴다.
- 다른 브랜치에 있으면 pull 이 조용히 그 브랜치를 당긴다 → checkout 명시
- 로컬 커밋이 얹혀 있으면 pull 이 병합 커밋을 만든다 → --ff-only 로 멈춘다
- 어디서 깨졌는지가 로그에 남는다
마지막에 `git log -1` 로 **어떤 커밋으로 깔았는지**를 작업 로그에 남긴다.

### 테스트 (820 → 827)
가짜 hub-provisioning 을 **진짜 git 저장소**로 바꿨다 (origin 을 자기 자신으로
걸어 네트워크 없이 성립). 안 그러면 최신화가 전부 막혀 실제 경로를 못 본다.

- `_needs_fresh_repo` 를 꺼서 빨간불 확인함

## 2026-08-28 — 본체 시리얼 (dmidecode) 표시

`sudo dmidecode -s system-serial-number` 로 타겟 본체 시리얼을 읽어
**서버 화면**과 **대시보드**에 띄운다.

### 어디서 읽나 (용혁님 선택)
- **키 등록 때 자동으로 한 번.** sudo 비밀번호를 쥐고 타겟에 붙어 있는 자리가
  거기뿐이다. 나중에 읽으려면 사람이 비밀번호를 다시 내놓아야 한다.
- **서버 목록의 `조회`(값이 있으면 `↻`) 버튼.** 키 등록 전에 만들어둔 서버와
  본체를 바꾼 서버용. 비밀번호를 따로 묻지 않는다 — 접속은 등록된 키로 하고
  sudo 에는 `.env` 의 SSH_PASSWORD(설치가 쓰는 그 값)를 쓴다.

### 왜 root 가 필요한가
dmidecode 는 /dev/mem 을 읽는다. 대안인 /sys/class/dmi/id/product_serial 도
0400 이라 일반 계정으로는 어느 쪽도 안 된다. 비밀번호는 `sudo -S -p ''` 의
**표준입력**으로 넘긴다 — 명령줄에 실으면 타겟의 `ps` 에 그대로 보인다
(절전 mask 와 같은 이유).

### 안 믿는 값
`Default string` · `To Be Filled By O.E.M.` · `System Serial Number` 등
제조사가 번호를 안 넣고 출고한 기계가 내놓는 문자열은 **저장하지 않는다.**
저장하면 서버마다 같은 값이 박혀서 다른 기계를 구분한다고 착각하게 된다.
표준출력만 파싱한다 — sudo·dmidecode 경고는 표준오류로 나오는데 그걸 값으로
읽으면 목록에 오류 문구가 시리얼로 박힌다.

### 화면
- 서버 표에 `시리얼` 칸 추가 (7칸 → 8칸, 빈 목록 colspan 도 같이).
  키가 없으면 버튼도 없다 — 접속 자체가 안 되므로.
- 대시보드: 최근 작업 표의 서버 이름 밑에 `SN …`, 진행 중 카드의 메타 줄에도.
  **지금 인벤토리에 기록된 값**이지 그 작업 때의 값이 아니라서 툴팁에 밝혔다.

### 코드
- 새 모듈 `node_info.py` (명령·파싱·실패 사유 한 곳에). ssh_keys 가 이걸 쓴다
  (반대 방향이면 순환 import).
- `AsyncSSHClient` 에 `key_path` 추가. asyncssh 는 `client_keys=None` 을 주면
  공개키 인증을 아예 안 하므로(known_hosts 와 같은 함정) 있을 때만 넘긴다.
- `server_meta.serial` 칸 + 마이그레이션. 이미 있는 행은 NULL 로 남는다.
- `POST /api/servers/{host}/serial`, `/api/servers` 응답에 `serial`.

### 테스트 (829 → 866)

## 2026-08-28 (이어서) — 키 등록 진행 표시 + AnyDesk ID 파싱 사고

### 1) AnyDesk ID 를 못 읽던 버그 (snuseoul 에서 발견)
`anydesk --get-id` 는 값 끝에 **개행을 안 붙인다.** 그 출력을 sed 로 흘려보낸
뒤 기계용 줄을 이어 찍었더니 한 줄로 붙었다:

    이 장비의 AnyDesk ID:
      1318618610ANYDESK_ID=1318618610

파서가 `^ANYDESK_ID=` 로 줄 머리에 고정돼 있어 못 잡았다. 등록은 성공했는데
**접속 ID 만 조용히 사라졌다** — 그 PC 에 원격으로 들어갈 길이 없어진다.

- node_prep.sh: ID 를 **한 번만** 물어 변수에 담고 echo 로 찍는다.
  ($( ) 가 끝 개행을 정리하고 echo 가 다시 붙인다)
- parse_anydesk_id: `match` → `search`. 스크립트를 고쳤어도 파서가 한 겹 더
  버티게 둔다. 이 값을 놓치면 사람이 할 수 있는 일이 없다.
- 실제 사고 출력을 그대로 테스트에 박았다. 가짜 anydesk(개행 없음)로 셸
  블록을 돌려 두 줄로 갈라지는 것도 확인했다.
- **이미 등록한 서버는 키를 다시 등록해야 ID 가 채워진다.**

### 2) 키 등록이 멈춘 것처럼 보이던 문제
hybrid 는 apt 로 AnyDesk(16MB)를 깐다 — 몇 분이다. 그동안 화면에는 눌린 버튼
말고 아무것도 없었다.

- **응답을 스트리밍으로 바꾸지 않았다.** 상태코드로 실패를 알리는 지금 구조가
  깨진다 (400/429 를 화면이 구분해 쓴다). 대신 진행 상태만 따로 적어두고
  (`web/progress.py`, 프로세스 메모리) 화면이 1초에 한 번 물어본다.
- `register_key(on_step=...)` 로 단계를 알린다. 단계 목록은 `steps_for(prepare)`
  가 정하고 — hybrid 만 `prep` 이 낀다 — 이름은 화면(KEY_STEPS)이 쥔다.
  ansible_log 단계와 같은 규칙이다. 테스트가 둘을 대조한다.
- 지금 나오는 출력 한 줄도 같이 보낸다 (apt 줄). **가려서** 보낸다 — 준비
  스크립트 출력에는 AnyDesk 비밀번호가 섞일 수 있다.
- 시계는 브라우저가 자체적으로 굴린다. 서버가 대답을 못 해도 멈춰 보이지 않는다.
- 끝나면(성공이든 실패든) 판을 지운다. 안 지우면 다음 등록이 옛 단계부터 보인다.

### 테스트 (867 → 887)
- 등록이 **도는 동안** 진행을 물어볼 수 있는지 (Event 로 붙잡아두고 조회)
- 실패로 끝나도 판이 치워지는지
- 진행 줄에 AnyDesk 비밀번호가 안 묻어 나가는지
- 단계 순서 (hybrid / onprem 각각)
- 서버가 내놓는 단계 키에 화면 이름이 다 있는지
- 붙어버린 실제 로그에서 ID 를 뽑아내는지
- 판 치우기·마스킹·prep 단계 알림·단계 이름을 각각 깨서 빨간불 확인함

## 2026-09-01 — 키 등록 진행 상자가 안 보이던 버그

증상: `SSH 키 등록` 에서 등록을 누르면 창에 **제목과 버튼만** 남는다. 사람은
"등록이 안 되는구나" 하고 닫기를 누른다 (heung-k 에서 발견).

원인: `#keyProg` 를 `hidden` 으로 만들어 두는데, 등록할 때 **폼만 숨기고 상자를

`[hidden]{display:none !important}` 라 화면에 안 나왔다.

고침: 펼치는 일을 **그리는 쪽**으로 옮겼다 (`watchKeySteps` 안에서
`box.hidden = false`). 부르는 쪽에 맡기면 또 빠뜨린다.

왜 테스트가 못 잡았나: 정적 문자열 검사는 DOM 상태를 못 본다. `watchKeySteps`
가 있는지, 불리는지는 봤지만 "그려진 것이 보이는지"는 볼 수 없었다. 적어도
펼치는 줄이 사라지는 것은 잡도록 테스트를 넣었다 (888).

## 2026-09-04 — 1.1.1.0 경계: patch 대신 configure

1.1.1.0 부터 **신규 이미지**가 들어왔다. patch 는 base↔new 의 diff 만 담으므로
새 이미지가 반영되지 않는다. 그 경계를 넘길 때는 configure 로 세 단계만 돌린다:

    ./bin/hubctl configure -e ENV -l HOST -K \
      --only gitops_publish,secrets_fetch_env_file,flux_wire \
      -- -e hub_deploy_ref=release/1.1.1.0

### 판단 기준 (용혁님 선택)
- **ref 로 자동 + 사람이 뒤집기.** ref 의 버전이 1.1.1.0 이상이면 configure 를
  미리 골라둔다. 이미 1.1.1.0 이상인 서버를 다음 버전으로 올릴 때는 patch 가
  맞는데 그건 ref 만 봐서는 알 수 없다 — 그래서 **기본 선택**일 뿐이고,
  한 번이라도 직접 고르면 자동으로 안 뒤집는다 (화면과 싸우지 않게).
- 1.1.1.0 을 건너뛰어도(1.1.0.x → 1.1.1.1) 경계를 넘으면 configure.
- 환경은 화면에서 고른다 (configure 는 `-e ENV` 필수, 기본 prod).
- `--only` 세 태그는 코드에 고정. 다른 태그는 서버가 거부한다 —
  콘솔이 임의의 단계를 돌리는 통로가 되면 안 된다.

### 버전 읽기
`release/1.1.1.0` · `v1.1.1.0` · `1.1.1` 에서 숫자만 뽑고 네 자리로 채운다.
`main` · `feature/…` 는 None → 기존 동작(patch). **지어내지 않는다.**

### 저장
`jobs.only_tags` 칸을 추가했다 (마이그레이션 + 재생성 때 옮기는 목록에도).
없으면 재시도가 같은 명령을 다시 만들지 못한다.

### 잡은 결함
`_execute` 가 명령을 **다시 조립**하는데 거기에 `only` 를 안 넘겼다. 생성 때
검증은 통과하고 실제로는 `--only` 없이 configure 전체가 도는 상태였다.
테스트(진짜 서브프로세스로 ARGS 를 확인)가 잡았다.

### 테스트 (889 → 916)
- 버전 파싱 9종 / 경계 판정 6종
- runbook 명령과 글자 그대로 일치하는지
- `--only` 가 `--` **앞**에 오는지 (뒤로 가면 ansible 로 넘어가 hubctl 이 못 본다)
- configure 외의 종류는 `--only` 를 거부하는지
- 허용 목록 밖 태그·빈 태그 거부
- 화면과 서버의 경계값·태그가 같은지 (갈라지면 화면 어디에도 안 보인다)
- 경계 이동·only 누락·`--only` 위치를 각각 깨서 빨간불 확인함

## 2026-09-04 (이어서 2) — `--only` 는 ref 를 바꾸는 데 쓰는 게 아니었다

installtest 에서 `configure --only ... -e hub_deploy_ref=release/1.1.1.0` 이
`flux_wire : partial_guard` 에 막혔다. 라이브 GitRepository 는 `branch: main`
인데 이번 실행 ref 가 `release/1.1.1.0` 이라 **ref 를 바꾸려 한 것**이고,
`--only` 는 그걸 하지 않는다.

hub-provisioning 자체 문서가 못박고 있다 (RUNBOOK-hubctl §3-8):
> ref 를 바꾸는 일은 --only 로 하지 않는다: 앱 버전 bump 는 hubctl patch,
> 신규 앱이 담긴 다른 ref 로 옮기는 건 --only 없는 전체 configure
> (어차피 미러 14분이 지배적이라 절감폭이 작다).

§3-8 표의 `-e hub_deploy_ref=<라이브 ref>` 도 "지금 그 사이트가 이미 보고 있는
ref" 라는 뜻이다. 내가 이걸 "올릴 ref" 로 읽었다.

### 고침
콘솔의 configure 모드는 이제 `--only` 를 **안 붙인다**. 전체 configure 로 돈다.
- 단계 표시도 2칸 → configure 전체 7칸.
- 모드 이름을 실제 규칙대로: patch = 앱 버전만, configure = 다른 ref 로 옮기기.
- 경고에 실제로 걸리는 것들을 적었다: 새 앱 시크릿이 그 env Vault 마운트에
  미리 있어야 하고(없으면 secrets_fetch 가 Invalid or missing path 로 중단),
  반영은 Flux 주기 최대 10분(즉시 확인은 flux reconcile), 재실행은 안전.

`build_command(only=...)` 자체는 남겨둔다 — hubctl 의 실제 기능이고 테스트가
규칙을 문서화한다. 다만 콘솔은 지금 아무 데서도 안 쓴다.

### 배운 것
문서를 읽을 때 `<라이브 ref>` 같은 자리표시자의 **뜻**을 확인하지 않았다.
가드 메시지가 그 자리에서 정확히 설명하고 있었는데, 그건 실행하고 나서야 봤다.
