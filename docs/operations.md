# AutoDeploy 웹 콘솔 — 운영 가이드

맥미니(컨트롤러)에서 병원 서버를 설치·검증·초기화하는 웹 콘솔의 설치와 운영.
설치 자체는 `~/hub-provisioning` 의 hubctl/Ansible 이 수행하고, 콘솔은 그것을
띄우고 진행상황을 보여주는 껍데기다. **타겟 PC 에서 직접 뭔가를 실행하지 않는다.**

- 개발지시서: `docs/specs/dev-spec-web-console-20260826.md`
- 비개발자용 수동 설치 절차: `runbook.md`

---

## 1. 준비

### 1-1. 필요한 것

| | |
|---|---|
| 컨트롤러 | 맥미니 (이 저장소 + `~/hub-provisioning`) |
| 파이썬 | 3.14 |
| Ansible | `ansible-playbook` 이 PATH 에 있어야 함 |
| 자격 | Vault · AWS(ECR) · Bitbucket — `hubctl preflight` 로 확인 |
| 타겟 | Ubuntu, `openssh-server` 동작, sudo 가능한 계정 |

### 1-2. `.env`

`.env.example` 를 복사해 채운다. 웹 콘솔이 쓰는 항목은 아래.

```
HUBCTL_REPO_PATH=~/hub-provisioning
BECOME_PASSWORD=            # 비우면 SSH_PASSWORD 사용 (connecteve 계정 공통)

WEB_ENABLED=true
WEB_HOST=0.0.0.0            # 맥미니 밖에서 접속하려면. 루프백만이면 127.0.0.1
WEB_PORT=8080
SESSION_TTL_DAYS=14
WEB_SECURE_COOKIE=false     # HTTPS 프록시 뒤에 둘 때만 true
WEB_TRUST_FORWARDED=false   # 신뢰하는 프록시 뒤에 둘 때만 true
WEB_PUBLIC_URL=http://100.116.199.41:8080   # Slack 메시지에 넣을 콘솔 주소

# hybrid 타겟 PC 준비 (§7-1). onprem 에는 쓰이지 않는다.
ANYDESK_PASSWORD=                          # 무인 접근 비밀번호. 비우면 그 단계만 건너뜀
NODE_PREP_WEEKLY_REBOOT=false              # 주간 재부팅 크론. 기본 꺼짐
NODE_PREP_WEEKLY_REBOOT_CRON=0 4 * * 0
```

`.env` 는 `chmod 600` 으로 두고 저장소에 커밋하지 않는다.

**`WEB_HOST` 기본값이 `127.0.0.1` 인 이유** — 이 콘솔은 타겟 서버에 sudo 로
임의 변경을 가할 수 있다. 노출 범위는 실수가 아니라 선택이어야 한다.

### 1-3. 환경변수 상속 (중요)

hubctl 은 `VAULT_ADDR` · `VAULT_TOKEN` · `HUB_DEPLOY_GIT_TOKEN` · AWS 자격을
셸 환경에서 읽는다. 콘솔은 hubctl 을 `zsh -lc "<명령>"` 으로 감싸 실행한다.

**그런데 `zsh -lc` 는 `~/.zshrc` 를 읽지 않는다.** zsh 는 `.zshrc` 를
*대화형* 셸에서만 읽기 때문이다. 실제로 확인한 결과:

| 실행 방식 | `.zshenv` | `.zprofile` | `.zshrc` | `.zlogin` |
|---|---|---|---|---|
| `zsh -lc` (데몬이 쓰는 것) | ✅ | ✅ | **❌** | ✅ |
| `zsh -ic` | ✅ | ❌ | ✅ | ❌ |

macOS 에서 `export` 를 두는 기본 자리가 `.zshrc` 라서, **터미널에서 되는데
콘솔에서만 안 되는** 일이 생긴다. 자격을 `.zshrc` 에만 넣어두면 콘솔은 못 본다.

#### 자격을 콘솔에 전달하는 방법

**`.env` 에 넣는 것을 권한다.** 데몬은 기동할 때 `load_dotenv()` 로 `.env` 를
`os.environ` 에 올리고, hubctl 자식 프로세스는 그 환경을 그대로 물려받는다.
셸 설정 파일이 뭘 읽는지 따질 필요가 없어 가장 확실하다.

```
VAULT_ADDR=https://vault.connecteve.com
VAULT_TOKEN=
HUB_DEPLOY_GIT_USER=x-bitbucket-api-token-auth
HUB_DEPLOY_GIT_TOKEN=
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
```

`VAULT_TOKEN` 은 만료되므로 `vault login` 을 다시 할 때마다 갱신해야 한다.

`~/.zprofile` 이나 `~/.zshenv` 에 `export` 하는 것도 동작한다 — 위 표에서
`zsh -lc` 가 읽는 파일이다. `.zshrc` 는 안 된다.

#### 실행 파일 경로

`ansible-playbook` · `aws` 는 launchd 가 주는 `PATH` 에서 찾는다. plist 는
`/opt/homebrew/bin` 을 포함한다 (Apple Silicon 의 Homebrew 위치). 다른 곳에
설치했다면 plist 의 `PATH` 에 추가하고 `autodeploy install` 로 다시 등록한다.

#### 지금 데몬이 뭘 보는지 확인하기

```bash
zsh -lc 'echo "VAULT_ADDR=${VAULT_ADDR:-없음}";
         echo "HUB_DEPLOY_GIT_TOKEN=${HUB_DEPLOY_GIT_TOKEN:+설정됨}";
         echo "ansible-playbook: $(command -v ansible-playbook || echo 없음)";
         echo "aws: $(command -v aws || echo 없음)"'
```

토큰 값은 찍지 않는다 — 설정 여부만 본다.

### 1-4. 버전

버전은 `src/autodeploy/__init__.py` 의 `__version__` 하나가 기준이고,
`pyproject.toml` 이 같은 값을 들고 있어야 한다 (테스트가 대조한다).

화면에는 로고 아래 `설치 콘솔 v1.0.0` 로 뜬다.

- 콘솔은 `/api/me` 에 실려 오는 값을 쓴다 (이미 부르는 요청이라 늘리지 않았다)
- 로그인 화면은 세션이 없어 `/api/me` 를 못 부르므로 공개 `/healthz` 에서 받는다

올릴 때는 **두 파일을 같이** 고치고 데몬을 다시 띄운다. 화면은 새로고침만 하면 된다.

## 2. 계정

웹 화면에는 계정 관리가 없다. 터미널에서만 만든다.

```bash
autodeploy adduser yonghyuk     # 비밀번호는 프롬프트로만 입력
autodeploy passwd  yonghyuk     # 변경 시 그 사용자의 세션이 전부 끊긴다
autodeploy deluser yonghyuk
autodeploy users
```

- 비밀번호는 인자로 받지 않는다 — 셸 히스토리와 `ps` 목록에 남지 않게 하기 위함.
- 저장은 scrypt 해시(n=2^14)뿐이다. 평문도, 복호화 가능한 형태도 남기지 않는다.
- 로그인 실패가 (IP, 아이디) 조합으로 5회 쌓이면 60초 잠긴다.

### 2-1. 지난 로그의 오류 분류 다시 매기기

```bash
autodeploy fixlogs          # 전체
autodeploy fixlogs 33       # 특정 작업만
```

로그 줄의 `kind`(오류/경고/성공 분류)는 줄 내용에서만 유도되는 **표시용** 값이다.
파서를 고치면 그 뒤 작업부터 정상이 되지만, **이미 저장된 줄은 옛 분류를 그대로
들고 있어** 지난 작업 화면의 오류 요약이 계속 틀리게 보인다. 이 명령이 저장된
줄을 현재 파서로 다시 매긴다.

로그 원문(`line`)과 `stream`(stdout/stderr)은 건드리지 않는다 — `stream` 은
Slack 경로가 쓰는 원본 정보다. 두 번 돌려도 결과가 같다.

## 3. 기동

### 3-1. 손으로 띄우기 (확인용)

```bash
cd ~/deploy
python -m autodeploy
```

로그에 `웹 콘솔: http://127.0.0.1:8080` 이 뜨면 브라우저로 접속한다.

### 3-2. launchd (상시)

기존 `com.connecteve.autodeploy` 데몬이 웹 콘솔을 함께 띄운다.
**별도 프로세스가 아니다** — 별도로 띄우면 같은 SQLite 파일을 두 프로세스가
쓰게 되어 잠금이 엉킨다.

```bash
launchctl unload ~/Library/LaunchAgents/com.connecteve.autodeploy.plist
launchctl load   ~/Library/LaunchAgents/com.connecteve.autodeploy.plist
```

웹 기동에 실패해도 Slack 봇은 계속 돈다. 실패 이유는 데몬 로그에 남는다.

### 3-3. Slack 없이 웹 콘솔만 쓰기

`.env` 에 `SLACK_ENABLED=false` 를 넣고 데몬을 다시 띄운다. 봇도, 웹 작업의
Slack 게시도 뜨지 않고 콘솔만 돈다. 이때 `SLACK_BOT_TOKEN` 등 `SLACK_*` 는
아예 없어도 된다 — 쓰지도 않을 토큰을 발급받게 하지 않는다.

```
SLACK_ENABLED=false
WEB_ENABLED=true
```

되돌리려면 `true` 로 바꾸고 다시 띄우면 된다. 값을 안 넣으면 `true` 로 본다.

> **끄기 전에 웹 콘솔로 실 서버 설치를 한 번 성공시켜 두는 편이 낫다.**
> v1 Slack 경로는 `setup-*.sh` 를 SSH 로 실행하고, 웹 콘솔은
> hubctl/Ansible 로 실행한다 — **설치 방식 자체가 다르다.** Slack 을 먼저
>끄면 문제가 생겼을 때 돌아갈 경로가 없다.

`SLACK_ENABLED=false` 와 `WEB_ENABLED=false` 를 함께 두면 이 프로세스가 할 일이
없다. 그 경우 조용히 떠 있지 않고 종료 코드 2 로 끝난다 — KeepAlive 가 살려두는
바람에 "돌고는 있는데 아무 반응이 없는" 상태로 오래 남는 것을 막기 위함이다.

### 3-3-1. `WEB_HOST` — 어디까지 열 것인가

| 값 | 닿는 곳 | 비고 |
|---|---|---|
| `127.0.0.1` | 맥미니 자기 자신만 | 기본값 |
| `0.0.0.0` | **사내망 전체 + tailnet** | 평문이라 같은 망이면 누구나 붙는다 |
| `100.116.199.41` | **tailnet 만** | 권장 — 사내망 노출이 사라진다 |

tailnet 주소로 묶으면 맥미니 자신에서도 `127.0.0.1:8080` 으로는 안 열린다.
`http://100.116.199.41:8080` 을 쓴다.

부팅 직후 Tailscale 인터페이스가 아직 없으면 바인딩이 실패한다. 그때는 데몬이
종료 코드 2 로 끝나고 launchd 가 `ThrottleInterval`(10초) 뒤에 다시 띄운다 —
Tailscale 이 올라오면 저절로 붙으므로 손댈 것이 없다.

`WEB_HOST` 는 포트포워딩 중계 리스너에도 그대로 쓰인다(`forward_bind`).
콘솔보다 중계가 더 넓게 열리는 일이 없도록 일부러 같은 값을 쓴다.

### 3-4. 맥미니 밖에서 접속하기 (사내 LAN · Tailscale)

`WEB_HOST=0.0.0.0` 으로 바꾸고 데몬을 다시 띄우면 맥미니가 가진 모든 주소로 열린다.

| 경로 | 주소 |
|---|---|
| 맥미니 자신 | `http://127.0.0.1:8080` |
| 사내 LAN | `http://192.168.100.239:8080` |
| Tailscale (사외 포함) | `http://100.116.199.41:8080` |

`WEB_PUBLIC_URL` 에는 이 중 **하나**를 골라 적는다. Slack 종료 메시지의
"웹 콘솔에서 로그 보기" 링크가 이 값으로 만들어지므로, 사외에서도 눌러야 한다면
Tailscale 주소를 적는다. `0.0.0.0` 은 "모든 인터페이스"라는 뜻이지 주소가 아니라서
비워두면 링크 자체가 안 붙는다.

Tailscale 로 접속하려면 **보는 쪽 기기도 같은 tailnet 에 로그인**돼 있어야 한다.
tailnet 밖에서는 이 주소가 아예 라우팅되지 않는다 — 그래서 아직 HTTPS 없이 쓸 수 있다
(§3-6 은 tailnet 이 아니라 진짜 공인 IP 로 열 때의 이야기다).

> `WEB_HOST` 에 Tailscale 주소(`100.116.199.41`)를 직접 적으면 tailnet 으로만 열려
> 더 좁다. 다만 맥미니 재부팅 시 Tailscale 이 인터페이스를 올리기 전에 데몬이 먼저
> 뜨면 바인드가 실패하고, 그 실패는 Slack 봇을 죽이지 않고 조용히 넘어간다 —
> 사람이 알아채고 데몬을 다시 띄우기 전까지 콘솔만 죽어 있다. `0.0.0.0` 을 권한다.

### 3-5. 포트포워딩 — 밖에서 타겟 UI·터미널 열기

설치가 끝나면 타겟에 traefik 이 `8000`(프론트) · `8001`(Temporal) · `8002`(WebPACS) ·
`8003`(Grafana) 를 연다. 여기에 그 PC 의 `22`(터미널)까지, 전부 **사내망 안에서만** 닿는다.

콘솔은 사내망 안(맥미니)에 있으면서 Tailscale 로 밖에서도 닿으므로, 그 사이를
잇는 임시 중계를 열 수 있다. **작업 상세 화면 → `포트포워딩`** (성공한 작업에만
뜬다 — 그전에는 타겟에 포트가 없다).

`열기` 를 누르면 맥미니에 리스너가 하나 열리고 주소가 표시된다. 그 주소의 호스트는
**지금 콘솔에 접속한 것과 같은 주소**다. Tailscale 로 들어와 있으면 그대로 열린다.

#### 포트마다 갈 곳이 다르다 (프로파일 × 환경)

`hybrid` 는 앱이 사이트가 아니라 중앙에 있다. 중계할 대상이 사이트에 없으므로
중계 버튼 대신 **공인 주소 링크**가 뜬다. 판정은 서버가 한다 — 화면이 규칙을
들고 있으면 주소가 바뀔 때 두 군데를 고쳐야 하고, API 로는 여전히 뚫린다.

| 포트 | onprem | hybrid dev | hybrid stage | hybrid prod |
|---|---|---|---|---|
| 8000 프론트 | 중계 | `dev-gateway.connecteve.com` | `stage-gateway.connecteve.com` | `hub.connecteve.com` |
| 8001 Temporal | 중계 | `dev-temporal-web.…` | `stage-temporal-web.…` | `temporal-web.…` |
| 8002 WebPACS | 중계 | **중계** | **중계** | **중계** |
| 8003 Grafana | 중계 | `dev-grafana.…` | `stage-grafana.…` | `grafana.…` |
| 22 터미널 | 중계 | **중계** | **중계** | **중계** |

`8002` 와 `22` 만 hybrid 에서도 중계다. 영상은 병원 안에 남고, 터미널로 들어갈
그 PC 자체는 중앙에 없기 때문이다.

주소를 바꾸려면 `src/autodeploy/web/forwards.py` 의 `CLOUD_URLS` 한 곳만 고치면
된다. 화면과 API 검증이 같은 표를 본다.

**환경을 모르면 열지 않는다.** `verify` · `clean` 처럼 `-e ENV` 를 받지 않는
작업에서 연 화면이면 hybrid 의 중앙 포트는 주소를 정할 수 없다. 그때는 중계를
내주는 대신 이유를 표시한다 — 중계해봐야 사이트 traefik 이 404 를 돌려줘
사람을 헷갈리게 할 뿐이다. 설치/구성 작업 화면에서 열면 된다.

#### 터미널 — 맥의 Terminal 앱이 열린다

`터미널 열기` 는 브라우저 탭을 여는 대신 **이 맥의 Terminal 앱**을 띄우고
접속까지 실행한다. macOS 가 `ssh` 스킴을 Terminal.app 에 물려두고 있어서,
콘솔이 `ssh://<사용자>@<콘솔주소>:<중계포트>` 를 넘기면 터미널 창이 뜨면서
`ssh -p <중계포트> <사용자>@<콘솔주소>` 가 그대로 돌아간다. 브라우저가 한 번
"Terminal 을 여시겠습니까?" 를 묻는다. 사용자 이름은 인벤토리의 `ansible_user` 다.

**타겟 비밀번호는 직접 입력해야 한다.** 중계는 타겟의 sshd 까지 길만 내주고,
인증은 여전히 내 맥 ↔ 타겟 사이에서 일어난다. 맥미니에 심긴 컨트롤러 키는
맥미니가 ansible 을 돌릴 때 쓰는 것이라 이 접속에는 관여하지 않는다.

비밀번호를 매번 치기 싫으면 **중계가 열려 있는 동안** 내 공개키를 한 번 심는다:

```
ssh-copy-id -p <중계포트> <사용자>@<콘솔주소>
```

맥이 아닌 기기(아이패드·윈도우)에는 `ssh://` 를 받아줄 앱이 없다. 그래서 포트 줄
밑에 접속 명령을 그대로 적어둔다 — 복사해서 쓰면 된다.

#### 무엇을 막아두었나

이 기능은 콘솔이 병원망으로 내는 길이라 범위를 좁게 잠가두었다.

- **포트**는 위 다섯 개만. 네 개는 설치가 실제로 여는 traefik hostPort 이고,
  나머지 하나가 터미널(22)이다. 3306 이든 6443 이든 목록 밖이면 거절한다 —
  아니면 로그인한 사람이 병원망을 훑을 수 있다.
- **22 를 연 것과 콘솔 안에 셸을 단 것은 다르다.** 중계는 sshd 까지 TCP 를
  이어줄 뿐이고 인증은 그대로 남아 있다. 콘솔에 로그인했다는 것만으로 타겟에
  명령을 돌릴 수는 없다 — 타겟 자격증명이 따로 있어야 한다.
- **대상**은 인벤토리에 등록된 서버만. 임의의 IP 를 넣으면 404 다.
- **바인드 주소**는 웹 콘솔과 같다(`WEB_HOST`). 노출 범위는 운영자가 이미 내린
  결정이고 중계가 그보다 넓어지지 않는다. `0.0.0.0` 이면 사내 LAN 에서도 그 포트가
  보인다는 뜻이다.
- **30분 무사용이면 자동으로 닫힌다.** 연결이 붙어 있는 동안은 안 닫는다.
- **데몬이 내려가면 열린 중계도 전부 닫힌다.**

한 번에 (서버, 포트)당 하나만 열린다. 버튼을 두 번 눌러도 포트가 늘지 않는다.

> DICOM(`1113`)은 목록에 없다. 브라우저로 열 수 없는 원시 TCP 라 여기서 다룰 것이
> 아니다. 필요하면 `ssh -N -L 1113:<타겟>:1113 <계정>@<맥미니>` 를 쓴다.

#### tailnet 너머의 타겟

타겟이 사내 LAN 이 아니라 **Tailscale 로만 닿는 곳**에 있어도 된다. 맥미니가
SSH 로 닿기만 하면 나머지는 똑같다.

- **등록**: `주소` 에 Tailscale IP(`100.x.y.z`)나 MagicDNS 이름을 넣는다.
  대역 제한은 없다. 단 **포트는 못 붙인다** (`1.2.3.4:22022` 는 거절) —
  `ansible_host` 는 주소만이고 sshd 는 22 를 쓴다.
- **키 등록 · 설치**: 맥미니에서 그 주소로 SSH 할 뿐이라 그대로 된다.
  타겟 인증서 SAN 에는 `ansible_host` 가 들어간다(`k0s_phys_ip`) — Tailscale
  주소로 등록했으면 그 주소로 k0s API 에 접근할 수 있다는 뜻이다.
- **포트포워딩**: 맥미니 → `<tailscale 주소>:800x` 로 잇는다. traefik 은
  `hostIP` 를 지정하지 않아 `0.0.0.0` 에 붙으므로 tailscale0 에서도 열린다.

막힌다면 코드가 아니라 그 사이 길을 본다.

- **Tailscale ACL** — 맥미니 → 타겟의 22 · 8000~8003 이 허용돼 있는지.
- **타겟 방화벽** — `ufw`/`firewalld` 가 그 포트를 막고 있는지.
- 타겟이 tailnet 에 실제로 올라와 있는지 (`tailscale status`).

### 3-6. 외부 고정 IP (아직 하지 말 것)

세션 쿠키가 평문으로 흐르면 계정이 그대로 털린다. 외부에 노출하려면
**HTTPS 리버스 프록시를 반드시 앞에 둔다.** 그 다음
`WEB_SECURE_COOKIE=true`, `WEB_TRUST_FORWARDED=true` 로 바꾼다.

`WEB_TRUST_FORWARDED` 는 프록시가 없을 때 켜면 안 된다 — 클라이언트가
`X-Forwarded-For` 를 위조해 로그인 잠금을 그냥 우회한다.

## 4. 서버 등록 (설치 전 1회)

1. **서버** 화면 → `＋ 서버 추가`
   - 이름(`inventory_hostname`) · 주소 · 계정 · `site_name` · 프로파일
   - 프로파일: `onprem` | `hybrid-with-ai` | `hybrid-without-ai`
   - 저장하면 `~/hub-provisioning/inventory/sites.yml` 이 갱신되고
     `sites.yml.bak-<타임스탬프>` 백업이 남는다 (최근 10개 유지).
2. **SSH 키 등록** — 목록의 `키 등록` 버튼, 타겟 비밀번호 1회 입력
   - 맥미니 공개키를 타겟 `~/.ssh/authorized_keys` 에 추가하고,
     비밀번호를 끄고 키만으로 재접속해 확인한 뒤에야 등록으로 인정한다.
   - 같이 **절전을 끄고**, **본체 시리얼도 읽어둔다** (아래 4-1).
   - 두 번 눌러도 줄이 늘지 않는다.
   - 비밀번호는 저장하지 않는다. 3회 실패하면 60초 잠긴다.
   - **진행 단계가 창에 보인다**: 타겟 접속 → 공개키 설치 → 절전 끄기 →
     본체 시리얼 → (hybrid 면) PC 준비 → 키 인증 확인. 경과 시간과 지금 나오는
     출력 한 줄도 같이 뜬다. hybrid 는 apt 로 AnyDesk(16MB)를 받느라
     **몇 분 걸린다** — 멈춘 게 아니다. 창을 닫아도 등록은 계속된다.

**키를 등록하지 않으면 설치를 시작할 수 없다.** 30분 돌리고 나서 SSH 로
죽는 것보다 시작 전에 걸러내는 편이 낫기 때문이다.

### 4-1. 본체 시리얼

납품한 기계를 나중에 특정하는 번호다. 타겟에서 이렇게 읽는다.

```
sudo dmidecode -s system-serial-number
```

- **읽는 때**: 자동이다. SSH 키 등록 때 한 번 읽고, 그때 못 읽었거나 그 전에
  등록해둔 서버는 **콘솔을 열 때** 뒤에서 채운다 (키가 등록된 서버만, 브라우저
  세션당 한 번). 버튼을 눌러야만 하면 서버 화면에 들르지 않는 한 대시보드에는
  영영 안 뜬다.
- **버튼**: 서버 목록 `시리얼` 칸의 `조회`(값이 있으면 `↻`). **본체를 바꿨을 때**
  와 자동 조회가 실패했을 때 쓴다.
- **보이는 곳**: 서버 화면의 `시리얼` 칸, 대시보드의 최근 작업 표(서버 이름 밑
  `SN …`)와 진행 중 카드.
- **비밀번호**: 조회 버튼은 따로 묻지 않는다. 접속은 등록해둔 키로 하고,
  sudo 에는 설치가 쓰는 것과 같은 `.env` 의 `SSH_PASSWORD`(또는
  `BECOME_PASSWORD`)를 쓴다. 값이 비어 있으면 무엇을 채워야 하는지 알려준다.
- **root 가 필요한 이유**: dmidecode 는 `/dev/mem` 을 읽는다. 대안인
  `/sys/class/dmi/id/product_serial` 도 0400 이라 일반 계정으로는 어느 쪽도 안 된다.
  비밀번호는 명령줄이 아니라 표준입력으로 넘어간다 (타겟의 `ps` 에 안 보인다).

**안 뜨는 경우**

| 화면에 나오는 말 | 뜻 |
|---|---|
| `dmidecode 가 없습니다` | 타겟에 패키지가 없다. `sudo apt install dmidecode` |
| `시리얼이 기록돼 있지 않습니다` | 제조사가 메인보드에 번호를 안 넣었다 (`Default string` 등). 콘솔이 할 수 있는 일이 없다 |
| `sudo 를 쓰지 못했습니다` | `.env` 의 비밀번호가 그 타겟의 것과 다르다 |

`Default string` 같은 값은 **저장하지 않는다.** 저장하면 서버마다 같은 문자열이
박혀서, 서로 다른 기계를 구분한다고 착각하게 된다.

### 주의

- **진행 중 작업이 있으면 서버 목록을 못 고친다** (409). 작업이 끝난 뒤에 한다.
- **호스트명은 바꿀 수 없다.** 작업 이력과 키 등록 상태가 이름으로 묶여 있다.
  바꿔야 하면 삭제 후 다시 추가한다.
- 서버를 삭제하면 인벤토리에서만 빠진다. **서버 내용은 그대로다.**
  내용을 지우려면 `서버 초기화` 를 먼저 실행한다.

## 5. 작업

### 5-1. 설치

**새 설치** 화면에서 서버를 고르고(여러 대 가능) 환경·ref 를 정한 뒤 시작한다.

- 여러 대를 고르면 **작업 하나에 `-l a,b,c`** 로 넘어간다. ansible 이 병렬로
  처리하며 기본 forks 는 5라, 6대 이상이면 5대씩 나눠 돈다.
- 환경(`-e`)과 ref 는 **실행당 하나**라 고른 전부에 공통 적용된다.
  서로 다른 환경이 필요하면 작업을 나눈다.
- 한 대가 실패해도 나머지는 계속 간다.
- **목록에는 서버마다 한 줄로 나온다.** 작업은 하나지만(번호가 같다) 상태는
  서버별로 갈린다. 그 줄을 누르면 **그 서버로 필터된 로그**가 바로 열린다.
  묶음의 첫 줄에만 체크박스가 있다 — 삭제 단위는 서버가 아니라 작업이다.
- `프로파일` 칸은 **실행 시점에 기록해 둔 값**이다. 나중에 서버를 `onprem` 에서
  `hybrid-with-ai` 로 바꿔도 지난 작업이 무엇으로 설치됐는지는 바뀌지 않는다.
  2026-08-26 이전 작업에는 이 기록이 없어서 지금 인벤토리 값을 `onprem?` 처럼
  점선 태그로 보여준다 — 기록이 아니라 현재 값이라는 표시다.
- 도는 도중에 한 대가 죽으면 **그 자리에서** 실패로 바뀐다. `PLAY RECAP` 은 맨
  끝에만 오므로, 그것만 기다리면 40분짜리 설치에서 5분 만에 죽은 서버가 끝까지
  '실행 중' 으로 보인다. 최종 판정은 여전히 RECAP 이 한다 — 도는 동안의 표시는
  임시다. `ignore_errors` 로 무시된 실패는 칠하지 않는다.

### 5-1-1. 시작 전 hub-provisioning 최신화

**설치·configure·patch 는 시작 직전에 컨트롤러의 `~/hub-provisioning` 을
`origin/main` 최신으로 맞춘다.** 맞추지 못하면 **시작하지 않는다.**

```
git fetch origin main
git checkout main
git merge --ff-only origin/main
git log -1 …            ← 이 줄이 작업 로그에 남는다
```

`git pull` 한 방으로 하지 않는 이유가 셋 있다.

- 다른 브랜치에 있으면 pull 이 조용히 그 브랜치를 당긴다 → `checkout` 을 명시
- 로컬 커밋이 얹혀 있으면 pull 이 병합 커밋을 만든다 → `--ff-only` 로 대신 멈춘다.
  컨트롤러가 baseline 에서 벗어났다는 뜻이라 사람이 봐야 한다
- fetch·checkout·merge 중 **어디서 깨졌는지**가 로그에 남는다

`inventory/sites.yml` 은 저장소의 `.gitignore` 에 있어 이 과정이 등록된 서버
목록을 건드리지 않는다.

**최신화가 실패하면 작업이 `실패` 로 끝난다.** 타겟 서버는 건드리기 전이라
반쯤 된 상태가 남지 않는다. 원인(네트워크·로컬 수정 등)을 고치고 다시 실행한다.

**점검·복구는 막지 않는다.** `verify`·`clean`·`rollback` 은 최신화를 하지 않는다 —
Bitbucket 이 죽었을 때 오히려 더 필요한 작업이라, 최신화 실패로 손발을 묶으면 안 된다.
`patch` 의 **적용 승인**(2단계 반입)도 하지 않는다. 번들은 생성 시점의 playbook 으로
만들어졌으므로 그 사이에 저장소를 바꾸면 앞뒤가 어긋난다.

시점이 **실행 직전**인 것도 이유가 있다. 작업 생성 시점에 당기면, 앞 작업이 도는
중에 playbook 파일이 발밑에서 바뀐다. 작업은 한 번에 하나만 돌므로 실행 직전이면
그럴 일이 없다.

### 5-2. 진행 보기

작업 상세에서 실시간 로그가 흐른다.

- **갱신 단위는 TASK 다.** 긴 TASK 중에는 수 분간 화면이 정적인 것이 정상이다.
  그래서 "마지막 출력 N초 전" 을 함께 보여준다 — 60초부터 강조되고 120초부터
  안내 문구가 붙는다. **멈춘 것이 아니다.**
- 화면에는 **대상 한 대의 줄만** 보인다. 컨트롤러 공통 줄은 항상 함께 보인다.
  여러 대를 한 작업으로 돌렸으면 호스트 칩으로 대상을 바꾼다 (한 대면 칩이 없다).
  여러 대 로그를 한 화면에 섞어 보는 모드는 없앴다 — 줄이 번갈아 끼어 읽을 수
  없었다. 섞인 원문이 필요하면 `로그 내려받기` 를 쓴다.
- 연결이 끊겨도 브라우저가 마지막 줄 번호로 다시 붙어 이어서 받는다.
- 전체 로그는 `로그 내려받기` 로 받는다.

#### 진행 단계 (설치 9단계)

| 단계 | 하는 일 | 실측 비중 |
|---|---|---|
| 사전 점검 | hubctl preflight 게이트 | 1% |
| 서버 기본 구성 | os_base · tools_aqua · network · time · storage | 12% |
| k0s 클러스터 | k0s | 1% |
| 클러스터 스토리지 | cluster_storage · k0s_airgap_export | 1% |
| **GitOps 적재** | zarf_init · gitops_publish · app_charts_fetch | **42%** |
| Flux 설치 | flux_install | 2% |
| **플랫폼 컴포넌트** | platform_secrets · shared_storage · platform_component · otel | **34%** |
| 연동 | consul_seed · secrets_fetch · temporal_register · flux_wire | 5% |
| 검증 | verify | 1% |

화면의 `12%`·`42%`·`34%` 는 **진행률이 아니라 소요 비중**이다 — 그 단계가 전체
설치 시간에서 차지하는 몫이다. 10% 넘는 단계에만 붙고, 목록 위에 `소요 비중`
이라는 열 제목이 함께 뜬다.

비중은 실서버 설치 로그(20분, 1627줄)를 다시 흘려 잰 값이다. **균등하지 않다** —
`GitOps 적재` 와 `플랫폼 컴포넌트` 가 합쳐서 76% 다. 앞 네 단계가 빨리 지나갔다고
곧 끝나는 것이 아니라서, 오래 걸리는 단계에는 화면에 비중을 함께 표시한다.

단계는 ansible 의 `TASK [<롤> : ...]` 줄에서 읽는다 (`ansible_log.ROLE_STEPS`).
PLAY 는 install 에 둘(Bootstrap·Configuration)뿐이라 그것만으로는 큰 덩어리
셋밖에 안 나왔다. **단계는 뒤로 가지 않는다** — 같은 롤이 뒤에서 또 돌아도
표시가 되돌아가지 않는다.

> 롤 이름은 hub-provisioning 것이라 그쪽에서 롤을 새로 만들거나 이름을 바꾸면
> 그 구간이 이전 단계에 머문다. 진행이 멈춘 것처럼 보일 뿐 설치는 정상이며,
> `ROLE_STEPS` 에 이름을 추가하면 된다.

### 5-3. 취소

`작업 취소` 는 ansible 프로세스 그룹을 종료한다.
**여러 대를 대상으로 하는 작업이면 전부 중단된다** — 프로세스가 하나라
서버별로 나눠 멈출 수 없다. 이미 적용된 변경은 되돌아가지 않는다.

### 5-4. 재시도

실패한 작업 상세에 `실패한 N대만 재시도` 가 뜬다. Ansible 은 멱등해서
이미 끝난 부분은 건너뛴다. 전체 재시도도 가능하다.

### 5-4-1. 1.1.1.0 경계 — patch 냐 configure 냐

**1.1.1.0 부터 신규 이미지가 추가됐다.** patch 는 base↔new 의 *변경분*만 번들에
담으므로, 새로 생긴 이미지는 들어가지 않는다. 그래서 그 경계를 넘을 때는
configure 로 세 단계만 다시 돌린다.

| 지금 깔린 버전 | 올릴 버전 | 명령 |
|---|---|---|
| 1.1.0.3 이하 | 1.1.1.0 이상 | `configure --only gitops_publish,secrets_fetch_env_file,flux_wire` |
| 1.1.1.0 이상 | 그 다음 | `patch` (기존) |

```
./bin/hubctl configure -e prod -l bumin-node1 -K \
  --only gitops_publish,secrets_fetch_env_file,flux_wire \
  -- -e hub_deploy_ref=release/1.1.1.0
```

**콘솔에서**: 패치 화면의 `적용 방식` 에서 고른다. ref 에 적은 버전이 1.1.1.0
이상이면 configure 가 미리 골라져 있고, 아니면 patch 다. **한 번이라도 직접
고르면 그 뒤로는 자동으로 안 바뀐다** — 이미 1.1.1.0 이상인 서버를 다음 버전으로
올리는 경우는 올릴 ref 만 봐서는 알 수 없기 때문이다. 그때는 patch 로 바꾼다.

configure 는 Vault 금고가 필요해서 `환경`(dev/stage/prod) 칸이 같이 나타난다.
`--only` 세 태그는 코드에 박혀 있고 다른 태그는 서버가 거부한다.

### 5-5. patch

설치가 끝난 서버에 **앱 버전만** 올릴 때 쓴다 (앱의 cpu/메모리 설정 변경도 같은
방법으로 반영된다). 앱이 추가·제거되는 등 구조가 바뀌면 patch 가 `패치 스코프
밖` 이라며 멈춘다 — 서버는 그대로이고, 그때는 `configure` 로 반영한다.

**패치** 화면에서 서버를 고르고 ref 를 적은 뒤 `패치 적용` 을 누른다. 콘솔은
터미널에서 쓰는 것과 **같은 원샷 명령**을 돌린다.

```
./bin/hubctl patch -l bumin-node1,bumin-node2 -- -e hub_deploy_ref=v1.2.1 -e hub_deploy_ref_type=tag
```

`-K` 는 붙지 않는다 — 콘솔은 become 비밀번호를 `ANSIBLE_BECOME_PASSWORD_FILE`
로 넘긴다. 터미널처럼 비밀번호를 두 번 묻는 일이 없다.

#### `[y/N]` 은 어디로 갔나

터미널에서는 번들을 만든 뒤 **변경 앱 요약**을 보여주고 `[y/N]` 을 묻는다.
콘솔은 그 확인을 **시작 버튼으로 옮겨왔다.** 시작하면 중간에 멈추지 않고
`y` 를 자동으로 넣는다. 작업 기록에 `... y 를 보냈습니다 (시작할 때 OO 님이
확인)` 로 남는다.

**변경 앱 목록은 실행 로그에 남지만, 보실 때는 이미 적용된 뒤다.** 목록을 먼저
보고 결정하고 싶으면 터미널에서 직접 실행한다.

되돌리려면 rollback 을 터미널에서 돌린다 (콘솔에는 아직 없다).

```
./bin/hubctl rollback -l bumin-node1 -K
```

#### 왜 `patch create` 가 아니라 원샷인가

둘은 같은 일을 하지 않는다. `patch-create.yml` 헤더에 그렇게 적혀 있다.

| | 원샷 `hubctl patch` | `hubctl patch create` |
|---|---|---|
| 어디서 도나 | 타겟에서 (become 필요) | 컨트롤러 로컬 |
| 비교 기준(base) | 지금 깔려 있는 live release-config | `-e patch_base=<ref>` 로 준 git ref |
| 용도 | 온라인 | **폐쇄망 반입용** |

병원들은 Tailscale 로 온라인이므로 원샷이 맞다. `patch create` 는
`-e patch_create_hosts=localhost` 를 하드코딩하고 그것이 passthrough 뒤에 붙어
나중 `-e` 가 이기므로, 밖에서 온라인 모드로 바꿀 수 없다.

폐쇄망 반입 경로(create → 승인 → apply)는 코드에 남아 있고 승인/거부/24시간
자동 취소도 그대로 돈다. 다만 **콘솔에서 그 상태로 들어가는 길은 없다.**

### 5-6. 초기화 (되돌릴 수 없음)

| 방식 | 지움 | 남김 |
|---|---|---|
| `reset` | 클러스터 · 앱 · 데이터 전부 | bootstrap 산출물 → 재설치가 빠름 |
| `reset` + `--keep-data` | 클러스터 · 앱 | `/data` · bootstrap 산출물 |
| `uninstall` | reset 이 지우는 것 + bootstrap 산출물 전부 | OS 기본 구성만 |

실행 전에 **호스트명을 직접 입력**해야 하고, 화면뿐 아니라 **서버에서도 다시
대조**한다. 한 번에 한 대만 가능하다.

### 5-7. 동시 실행

**작업은 한 번에 하나만 돈다.** 두 번째부터는 `대기` 상태로 줄을 선다.

서버 대수 제한이 아니다 — 여러 대 동시 설치는 "작업 하나에 `-l a,b,c`" 라
이 제한에 걸리지 않는다. 제한되는 것은 **작업 개수**다.

이유는 컨트롤러 쪽 자원이 겹치기 때문이다. `patch_apply` 가 `bundles/` 에서
mtime 최신 번들을 자동 선택하므로 패치가 겹치면 남의 번들을 적용할 수 있고,
`ecr_auth`·`secrets_fetch`·`gitops_publish` 등이 `delegate_to: localhost` 로 돈다.

### 5-8. 기록 지우기

대시보드 `최근 작업` 에서 지운다. 행 왼쪽 체크박스로 고른 뒤 `선택 삭제`,
또는 `전체 삭제`.

- **실행 로그가 함께 지워진다.** `job_events` · `script_logs` · `job_hosts` 가
  외래키 CASCADE 로 딸려 나간다. 되돌릴 수 없다.
- **진행 중인 작업(대기·실행·승인 대기)은 지워지지 않는다.** 러너가 그 작업
  번호로 로그를 계속 쓰는 중이라, 행을 지우면 다음 기록에서 죽고 실행이 통째로
  넘어간다. 골라도 건너뛰고 몇 건을 남겼는지 알려준다.
- `전체 삭제` 는 화면에 보이는 50건이 아니라 **끝난 것 전부**를 지운다.
  목록은 최근 50건만 받아오므로 그보다 오래된 기록까지 사라진다.
- **남겨둘 로그가 있으면 먼저 작업 상세에서 `로그 내려받기` 로 받아둔다.**
  내려받기는 DB 에서 읽으므로, 지우고 나면 받을 방법이 없다.
  (`~/Library/Application Support/autodeploy/joblogs/job-<번호>.log` 는 줄 수
  상한을 넘긴 **넘침분만** 담긴 파일이라 대부분의 작업에는 아예 없다.
  삭제와 무관하게 남지만 전체 로그가 아니다.)

## 6. Slack

웹에서 시작한 작업도 기존 채널에 게시된다.

- 시작 시 스레드 하나, 종료 시 그 스레드에 결과 한 줄 (호스트별 RECAP 포함)
- 로그를 통째로 흘리지 않는다 — 채널이 잠기고, 어차피 웹이 실시간 로그를 보여준다
- 작업 상세의 `Slack 스레드 열기` 는 Slack 이 알려준 정확한 링크를 쓴다
- Slack 이 죽어도 설치는 계속된다

기존 Slack 봇 명령(`install` 등)은 예전 경로 그대로 동작한다. 이번 작업에서
건드리지 않았다.

## 7. 문제 해결

| 증상 | 확인 |
|---|---|
| 로그인이 안 됨 | 5회 실패 후 60초 잠김. 계정은 `autodeploy users` 로 확인 |
| `서버 목록을 바꿀 수 없습니다` | 진행 중 작업이 있다. 메시지가 짚어준 `#번호` 를 열어 끝났는지 보고, 안 끝났으면 취소. 아래 참고 |
| `다른 곳에서 sites.yml 이 수정됐습니다` | 파일을 직접 고쳤거나 콘솔을 두 탭에 띄웠다. 새로고침 후 다시. **저장할 때마다 뜨면** 데몬이 옛 버전이다 (2026-08-26 이전) — 아래 참고 |
| `SSH 키가 등록되지 않은 서버` | 서버 화면에서 `키 등록` 먼저 |
| 키 등록 시 `Connection refused` | 타겟에 `openssh-server` 가 있는지, 포트가 열렸는지 |
| preflight 빨강 | 터미널에서 `hubctl preflight` 실행 → Vault 토큰 만료면 재로그인 |
| 로그가 멈춘 것 같음 | TASK 단위 갱신이라 정상일 수 있다. "마지막 출력 N초 전" 을 본다 |
| 작업이 계속 `진행 중` | 데몬이 죽었을 수 있다. 재시작하면 기동 시 정리된다 (아래) |
| `hub-provisioning 저장소를 찾을 수 없습니다` | `HUBCTL_REPO_PATH` 확인 |

### 서버 편집이 항상 `다른 곳에서 수정됐습니다` 로 막혔던 버그 (2026-08-26 수정)

인벤토리 저장은 낙관적 잠금을 쓴다 — 화면이 읽은 파일 시각(`st_mtime_ns`)을
저장할 때 되돌려주고, 서버가 실제 시각과 대조해 다르면 거절한다.

그 값을 **JSON 숫자**로 내보내고 있었다. 나노초 시각은 61비트인데 브라우저의
`JSON.parse` 는 숫자를 double 로 읽고, double 은 정수를 2^53 까지만 정확히
담는다. 이 크기에서 표현 가능한 값의 간격이 256ns 라 거의 항상 반올림된다.

```
서버가 보낸 값  1787751578430350197
브라우저가 읽은 값 1787751578430350000
```

그래서 화면이 되돌려준 값이 언제나 파일 시각과 달랐고, **서버 추가·편집·삭제가
100% 실패했다.** 지금은 문자열로 내보낸다 (화면은 이 값을 되돌려주기만 하고
계산에 쓰지 않는다).

파이썬 테스트로는 안 잡히던 종류다 — 파이썬 int 는 임의 정밀도라 서버끼리는
아무 문제가 없었다. 그래서 브라우저의 `JSON.parse` 를 흉내내는 테스트를 넣었다
(`like_a_browser`, `tests/test_web_servers.py`).

### 로그 마지막 줄이 잘려 있던 버그 (2026-08-27 수정)

작업이 끝나는 순간 마지막 0.15초치 로그가 통째로 사라질 수 있었다. 하필 거기
있는 것이 `PLAY RECAP` 과 오류 줄이라, 실패한 작업을 열었는데 왜 실패했는지가
안 보이는 일이 생겼다.

로그는 0.15초마다 모아서 넣는데, 그 함수가 버퍼를 통째로 꺼낸 **뒤에** DB 를
기다린다. 작업이 끝나면 수집 루프를 `cancel()` 했으므로, 하필 그 사이였으면
꺼내둔 줄이 어디에도 안 남고 사라졌다. 지금은 취소하지 않고 플래그로 세워
하던 일을 끝내게 한다 (`_LogSink.close`).

**이미 지난 작업의 잘린 로그는 되살릴 수 없다.** 다시 실행하면 정상이다.

### 재시작을 넘긴 작업 (서버 편집이 막힐 때)

데몬이 죽으면 그 작업을 감독하던 러너도 사라진다. 남은 것을 정리하지 않으면
영원히 `진행 중` 으로 보이고, **그동안 서버 추가·편집·삭제가 전부 막힌다**
(인벤토리가 흔들리면 화면의 목록과 실제 대상이 어긋나기 때문에 일부러 막아둔다).

기동할 때 자동으로 정리한다.

- `실행 중` · `승인 대기` → **실패**. 프로세스가 떴다가 감독자를 잃었다.
- `대기` → **취소**. 뜬 적이 없다. 큐는 메모리에만 있어서(`JobQueue._pending`)
  재시작하면 줄 서 있던 것이 사라진다. 되살아나지 않으므로 정리한다.
  다시 필요하면 그 작업 상세에서 `전체 재시도` 를 누르면 된다.

그래도 막히면 데몬을 한 번 재시작한다.

```
launchctl kickstart -k gui/$(id -u)/com.connecteve.autodeploy
```

### 로그 위치

- 데몬 로그: launchd 설정의 `StandardOutPath`
- 작업 로그: DB(`script_logs`). 한 작업이 20만 줄을 넘으면 이후는
  `<DB 디렉터리>/joblogs/job-<id>.log` 파일에만 쌓인다

### 서버가 설치 도중 잠들면

**`SSH 키 등록` 이 이걸 같이 해준다.** 키를 심는 김에

```
sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

를 돌린다 (멱등, 재부팅해도 유지). 그 단계는 이미 sudo 를 쓸 수 있는 비밀번호를
쥐고 타겟에 붙어 있어서 자리가 맞다. 웹 콘솔은 hubctl 을 돌릴 뿐이고 playbook 도
절전을 건드리지 않으므로, **자동으로 걸리는 자리는 여기뿐이다.**

**절전 끄기가 실패해도 키 등록은 성공시킨다.** 키가 없으면 설치를 아예 못 하는데
부수적인 설정 때문에 그걸 막을 이유가 없다. 대신 그때는 토스트가
"키 등록 완료 — 다만 절전 끄기는 실패했습니다" 라고 알리고 직접 실행할 명령을
보여준다. 보통 원인은 그 계정의 sudo 권한이다.

비밀번호는 **명령줄이 아니라 표준입력으로** 보낸다. `printf ... | sudo -S` 로
만들면 그 줄이 타겟의 `ps` 에 그대로 보이기 때문이다.

키를 이미 등록해 둔 서버(이 기능 이전)는 걸려 있지 않다. 타겟에서 위 명령을 한 번
실행하거나, 서버 화면에서 키를 다시 등록하면 된다.

### 7-1. hybrid 타겟 PC 준비 (AnyDesk 등)

`hybrid-with-ai` · `hybrid-without-ai` 로 등록한 서버는 **키 등록 때 준비
스크립트도 함께 돈다** (`src/autodeploy/node_prep.sh`). onprem 은 폐쇄망 서버라
해당 없다 — AnyDesk 저장소에 닿지도 않고 사람이 앞에 앉지도 않는다.

하는 일:

1. **GDM Wayland 끄기** (X11 강제). AnyDesk 는 Wayland 세션에서 화면 캡처가
   제한된다. **재부팅해야 반영된다** — 재부팅은 자동으로 하지 않는다.
2. **GNOME 절전·화면 잠금 해제.** 로그인 화면(gdm)과 사용자 세션(`connecteve`)은
   별개 경로라 둘 다 처리한다.
3. **AnyDesk 설치 + 무인 접근 설정.** 비밀번호는 `.env` 의 `ANYDESK_PASSWORD`.
4. **주간 재부팅 크론.** 기본은 **꺼짐** — 병원 장비를 정기 재부팅시키는 것은
   운영 정책이라 기본값으로 정할 일이 아니다.

`.env`:

```
ANYDESK_PASSWORD=...                       # 없으면 무인 접근 설정만 건너뛴다
NODE_PREP_WEEKLY_REBOOT=true               # 기본 false
NODE_PREP_WEEKLY_REBOOT_CRON=0 4 * * 0     # 일요일 04:00
```

`ANYDESK_PASSWORD` 는 마스킹 목록에 들어 있어 로그에 평문으로 남지 않는다.

**AnyDesk 접속 ID 는 서버 목록의 `메모` 칸에 자동으로 적힌다.** 메모와 따로
저장하므로 사람이 쓴 메모를 덮어쓰지 않고, 다시 등록해도 겹쳐 쌓이지 않는다.
실행이 끝나면 전체 로그가 창으로 뜬다 — 어느 단계를 건너뛰었는지가 거기 적혀 있다.

> **ID 를 못 읽었다고 나온 적이 있다 (2026-08-28 수정).** `anydesk --get-id` 가
> 값 끝에 개행을 안 붙여서, 사람이 읽는 줄과 기계용 줄이 한 줄로 붙었다
> (`    1318618610ANYDESK_ID=1318618610`). 등록은 성공했는데 ID 만 조용히
>사라졌다. 스크립트를 고쳤고 파서도 줄 머리에 고정하지 않게 바꿨다 —
> **그 전에 등록한 서버는 키를 다시 등록하면 ID 가 채워진다.**

**준비가 실패해도 키 등록은 성공시킨다.** 절전 끄기와 같은 이유다. 다시 등록하면
스크립트도 다시 돈다 (전부 멱등이라 중복되지 않는다).

비밀번호는 명령줄에 싣지 않는다. 스크립트를 표준입력으로 흘려 임시 파일
(`umask 077`)에 쓰고, sudo 비밀번호는 실행할 때 표준입력으로 준다. 파일은 끝나면
지운다 — 실패해도 지운다.

## 8. 백업 / 복구

| 대상 | 위치 | 비고 |
|---|---|---|
| 작업 이력 · 계정 · 세션 | `AUTODEPLOY_DB_PATH` (기본 `~/Library/Application Support/autodeploy/state.db`) | WAL 모드라 `-wal`·`-shm` 파일도 함께 복사 |
| 인벤토리 | `~/hub-provisioning/inventory/sites.yml` | 저장할 때마다 `.bak-*` 자동 생성 (10개 유지) |
| 스키마 변경 | — | 파괴적 마이그레이션 직전 `state.db.bak-<타임스탬프>` 자동 생성 |

DB 를 지우면 **작업 이력과 계정이 사라진다.** 서버 자체와 `sites.yml` 은 무관하다.
계정은 `autodeploy adduser` 로 다시 만들면 되고, 키 등록 상태(`server_meta`)는
사라지므로 서버별로 `키 등록` 을 한 번씩 다시 눌러야 한다 (타겟의
`authorized_keys` 는 그대로라 즉시 통과한다).

## 9. 보안 요약

- 세션 쿠키는 `HttpOnly` · `SameSite=Lax`. DB 에는 토큰의 sha256 만 저장한다.
- 변경 요청(POST/PUT/DELETE)에는 CSRF 토큰이 필요하다.
- 비밀은 `.env` 와 프로세스 환경에만 있다. `VAULT_TOKEN` · become 비밀번호 ·
  Bitbucket 토큰은 DB 적재 **전에** 로그에서 `***` 로 지운다.
- become 비밀번호는 0600 임시 파일로 넘기고 작업 종료 즉시 지운다.
  (파일에 실행 권한이 있으면 ansible 이 스크립트로 실행해버리므로 0600 은
  기밀성뿐 아니라 정확성 요건이다.)
- 모든 작업 생성·취소·승인은 사용자명과 함께 `jobs.started_by` / `job_events` 에 남는다.
- 이 콘솔은 타겟에 sudo 로 임의 변경을 가할 수 있다. **계정은 최소 인원에게만.**
